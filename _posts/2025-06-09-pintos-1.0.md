## Task 1: Alarm Clock

### 明确需求

我们需要重新实现 `devices/timer.c` 中 `timer_sleep()` 的实现.
目前它的实现方式是 "busy waiting", 即使用一个 `while` 循环来反复检查当前 `sleep` 时间是否超出要求.
如果某一时刻多个线程调用 `timer_sleep()`, 那么每一帧内 `while` 循环会被执行多次,
这带来了 CPU 的浪费.

当然这只是我的猜想, 我们还得用 gdb 验证一下. 也就是说, `thread_yield()` 是否会在一个 `tick`
内被反复执行.

![cgdb1](/assets/images/CS130/proj1_task1.1.png)

这里我以 alarm-mulitple 为例, 另外把函数的参数从 `ticks` 改成了 `sleep_ticks` (不然 `disp ticks`
不会正确显示我想要的 `static` 变量).

![cgdb2](/assets/images/CS130/proj1_task1.2.png)

先等待 `ticks` 变为 29, 因为第一次调用 `timer_sleep()` 的时候应该不可避免的需要一次 `thread_yield()`.
然后我数了一下, 这 tick 29 内, `thread_yield()` 一共被执行了 $28$ 次, 相当低效. 虽然我们只创建了 $5$
个线程, 但是每一 tick 内它们都被检查了不止一次.

### 分析

形式化的说, 假设我们有 $n$ 个线程, 每个线程 sleep 的时间为 $t_i$.
我们希望实现操作数 $\mathcal{O}(n + \max(t))$, 也就是只包含每个线程的 "挂起", "唤醒",
和总共 $\max(t)$ 次检查.

先考虑 $\max(t)$ 次检查, 我们把所有 sleeping 的线程放入一个等待队列, 每次 `ticks`
变化的时候检查是否有线程需要被唤醒就可以了.

关于等待队列的底层实现, 最容易想到的是二叉堆, 官方应该倾向于用链表实现.
如果你时间比较多的话可以来重新造一个轮子, 另外也请思考一下, 对于 pintos, 相比于时间复杂度,
空间复杂度是不是更应该考虑, 高效的内存利用是不是更重要?

最后想一下 "挂起" 与 "唤醒" 两个操作如何实现, 我发现 `thread.c` 中有两个函数 `thread_block()`,
`thread_unblock()` 似乎可以实现我的需求. 需要注意一下函数对应的注释中提到的
"This function must be called with interrupts turned off."
也就是说, `thread_block()` 的调用需要用 `old_level = intr_disable ();` 与
`intr_set_level (old_level);` 包裹. 如果想要了解更多信息可以看
[这里](https://pkuflyingpig.gitbook.io/pintos/appendix/reference-guide/synchronization).

## Task 2: Priority Scheduling

> 在开始之前, 请阅读
> [Synchronization](https://pkuflyingpig.gitbook.io/pintos/appendix/reference-guide/synchronization)
> 的有关信息

### 明确需求

用一句话概括就是实现符合直觉的, 支持抢占行为, 具有动态优先级的优先级调度系统 (round-robin scheduler).
但是动态优先级让这个系统变得有些麻烦, 一个线程的优先级可能会因为 `thread_get_priority()`,
`lock_acquire()` 而改变; 再加上支持抢占, `thread_create()`, `sema_up()`, `cond_signal()`
可能会造成重新调度 (但是 `thread_unblock()` 不会, 具体参考其注释).

### 分析

我们先来想一想怎么维护优先级, 由于 `struct lock` 的存在, 线程的执行一定有先后顺序,
或者说父子关系. 那么所有线程直接的执行顺序就形成了一片森林, 如果用一个虚拟节点连起来所有
`ready_list` 里面的线程, 那么就是一棵树了. (这里假设无环, 毕竟避免死锁不是操作系统而是用户的事情)

```text
   +-------+
   |Thread0|
   +---+---+
       |
       | (`locks_own`)
       |
    +--+---+     +------+     +------+     +------+
<---| head |<--->| Lock |<--->| Lock |<--->| tail |<--->
    +------+     +---+--+     +--+---+     +------+
                     |           |
        (`waiters`)  |           ~
                     |
                 +---+--+     +-------+     +------+
             <---| head |<--->|Thread1|<--->| tail |<--->
                 +------+     +---+---+     +------+
                                  |
                                  ~
```

可以这样理解线程之间的关系, 其中 `locks_own` 是我自己定义的变量. 再用 `extra_priority`
记录以当前线程为根的子树中最大优先级即可. 一个线程被锁住了, 沿着树向上爬更新信息;
一个线程放开锁了, 可能需要重新计算自己的 `extra_priority`, 我目前的实现是搜索一层子节点,
对于菊花图可能效率不佳. 为了更快的向上爬, 我给每个线程定义了 `parent` 变量,
这样可以跳过锁直接爬两层 (可惜这只是常数优化).

然后再想一想哪些时候需要询优先级. `thread_get_priority()` 与 `next_thread_to_run()` 比较显然,
然后 `thread_set_priority()` 与 `thread_create()` 由于抢占行为的存在也需要查询优先级,
最后就是 `sema_up()` 和 `cond_signal()` 了. 这里特别注意 `struct condition` 里面的链表存储的是
`struct semaphore` 并不是直接存储线程. (至少这个 `waiters` 的不一致让我的代码变 diry 了)

## Task 3: Advanced Scheduler

### 明确需求

我们需要实现一个类似于
[BSD scheduler](https://pkuflyingpig.gitbook.io/pintos/appendix/4.4bsd-scheduler)
的线程调度.

由于公式已经给出, 我们只需要完成定点数运算库之后开始套公式即可.

### 实现

关于定点数运算, 我感觉可以找 AI 写, 然后让它写几组数据来测试.

#### Priority

先表示出计算优先级的核心公式

```c
/* Calculate mlfq priority for thread T. */
static int
calc_mlfq_priority (struct thread *t)
{
  ASSERT (is_thread (t));
  if (t == idle_thread)
    return t->priority;
  /* The coefficients 1/4 and 2 on RECENT_CPU and NICE, respectively, have
     been found to work well in practice but lack deeper meaning. */
  int ret = PRI_MAX - FP_TO_INT (FP_DIV_INT (t->recent_cpu, 4)) - t->nice * 2;
  ret = min (ret, PRI_MAX);
  ret = max (ret, PRI_MIN);
  return ret;
}
```

发现我们需要维护 `nice` 与 `recent_cpu` 两个变量, 而在 `recent_cpu` 计算中我们还需要维护 `load_avg`.

#### Nice

- `nice` 的类型, 根据函数接口推断是 `int`.
- `nice` 的初始值, 有两种情况: `initial_thread` 与 others. 一个是 $0$, 另一个继承自父线程,
  寻找父线程只需要 `thread_current()` 即可.
- `nice` 的上下界 $\pm 20$, 它们应当被写入 `ASSERT()` 来检查.
- 关于 `nice` 的更新, 这里 `nice` 只会主动更新, 不需要动态计算.
- 需要完善的函数有 `thread_get_nice()`, `thread_set_nice()`.

#### Recent Cpu

- `recent_cpu` 的类型, 根据计算公式发现需要是定点数.
- `recent_cpu` 的初始值, 与 `nice` 一致.
- `recent_cpu` 似乎没有明显的上下界.
- `recent_cpu` 的更新, 有两种来源:
  - 发生 timer interrupt 时, 只要当前不是 `idle_thread` 在运行, 当前线程 `recent_cpu` 就需要 $+1$.
  - 每一秒 `timer_ticks () % TIMER_FREQ == 0` 时, 所有线程的 `recent_cpu` 都需要被更新.
- 需要完善的函数有 `thread_get_recent_cpu()`.

#### Load Avg

- `load_avg` 的类型, 根据计算公式发现需要是定点数, 而且需要是全局变量.
- `load_avg` 的初始值, 为 $0$.
- `load_avg` 似乎没有明显的上下界.
- `load_avg` 的更新, 在每一秒按照公式更新, 其中需要用到的 `ready_threads` 比较容易计算.
- 需要完善的函数有 `thread_get_load_avg()`.

### 一些问题

- `nice`, `recent_cpu` 的初始值有两种情况, 但是没有针对 "继承自父线程" 这种情况的测试, 最好检查一下.

## 可能有用的信息

- 对于一个 `struct thread`, 它申请的一页内存存储了这些信息.

  ```text
                    4 kB +---------------------------------+
                        |               aux               |
                        |            function             |
                        |            eip (NULL)           | kernel_thread_frame
                        +---------------------------------+
                        |      eip (to kernel_thread)     | switch_entry_frame
                        +---------------------------------+
                        |               next              | 
                        |               cur               |
                        |      eip (to switch_entry)      | 
                        |               ebx               | 
                        |               ebp               | 
                        |               esi               | 
                        |               edi               | switch_threads_frame
                        +---------------------------------+
                        |          kernel stack           |
                        |                |                |
                        |                |                |
                        |                V                |
                        |         grows downward          | 
  sizeof (struct thread) +---------------------------------+
                        |              magic              |
                        |                :                |
                        |                :                |
                        |               name              |
                        |              status             |
                    0 kB +---------------------------------+
  ```

- 如果调试的时候出现 value has been optimized out 的情况, 可以通过在合适的位置添加
  `__attribute__ ((noinline))` 来解决.
