## 源码结构

我们需要关注的源代码全部位于 `src/` 目录下, 后面我将把它作为根目录.

- `threads/`: 这里面包含了整个操作系统的程序入口. 而且实现了操作系统的的底层机制, 比如线程管理,
  同步与中断, 还有内存管理. 个人认为这个文件夹的核心是 `init.c`.
- `devices/`: 我感觉这里面的文件有点类似于驱动程序, 它让我们的操作系统得以与计算机里的硬件交互.
  个人理解, `threads/` 类似于操作系统的 "大脑", `devices/` 类似与操作系统的 "四肢".
  这一部分我们不需要了解太多, 最多就一个 `timer.c` 与 `block.c` 有查看的必要.
- `lib/`: 这个相对好理解, pintos 有一个自己的 C 库, 我们 `#include <>` 调用的就是这里面的文件.
  由于内核程序与用户程序可以调用的库范围不一致, 所以里面还有 `kernel` 与 `user` 加以区分,
  这两个文件夹之外的文件则是内核程序与用户程序可以共享的文件.
- `userprog/`: 这里的代码让用户程序得以被加载与运行. 对于一个与操作系统相对独立的 C 程序,
  它可以通过调用 system calls 来实现自己的功能 (需要完成 proj2 才可以正常工作). 简单来说,
  这个文件夹的核心是进程 `process.c` 与 `syscall.c`.
- `examples/`: 一些已经写好的用户程序, 它们只使用 pintos 内核提供的功能.
- `vm/`: 你似乎来到了没有代码存在的荒原. 不过问题不是很大, 虚拟内存本来就是有的.
- `filesys/`: 这里面实现了一个很基础的文件系统, 但是带有很多限制. 这里的核心就是 `filesys.c`.
- `utils/`: 这里有三个比较重要的脚本: `pintos`, `pintos-gdb`, `pintos-mkdisk`.
  具体内容不太需要了解.
- `tests/`: 运行测试, 并给你的代码打分. 如果你有测试点过不了建议研究一下里面的对应代码.
- `misc/`: 里面提供了 bochs 的安装脚本, 还有 Godmar Back 写的 `gdb` 扩展. 具体内容不太需要了解.
- `Makefile`: 这里有好几个 Makefile, 可惜的是在这个文件下下面 `make` 是得不到我们想要的结果的.
  我们需要在 `threads/`, `userprog/` 这些文件夹底下 `make`. 我认为这是因为 pintos 是一个教学用的
  操作系统, 我们一开始不需要了解整个 pintos, 也不需要用到所有代码. 所以需要 `-DUSERPROG`,
  `-DFILESYS` 来控制会被执行的代码. 而 `Makefile.kernel` 与 `Makefile.userprog`
  是用来区分系统内核与程序可以使用的 `lib/` 范围的.

## 启动流程

### 从硬件通电开始

```bash
cd src/threads
make
cd build
pintos -- -q
```

这个时候, `pintos -- -q` 究竟发生了什么.

首先我们知道 `pintos` 应该是一个 `perl` 脚本, 它可以调用 `bochs` 或者 `qemu` 作为模拟器来在一个
虚拟的机器上执行我们源代码编译生成的可执行文件. 至于我们编译生成的可执行文件, 其实有两个, 分别是
`loader.bin` 与 `kernel.bin`. 其中 `kernel.bin` 是一个 `DOS/MBR boot sector`
(可以用 `file` 命令查看), 这就是所谓的 bootstrap loader 了.

那么我们分析这个 `perl` 脚本做了什么, 首先处理传入的参数, 这个比较好理解.
后面的关键是通过 `assemble_disk (%disk);` 创建了一个虚拟的磁盘, 起始部分存放 `loader.bin`,
后面还存放了 `kernel.bin` 文件系统与交换分区 (在 proj1 应该不会用到), 还有启动参数 (传入的 `-q`).
准备好之后就可以运行模拟器了, 模拟器内置的 BIOS 会模拟硬件通电自检, 并发现虚拟磁盘开头存储了引导程序,
将其加载到内存中 (地址就是 0x00007c00 - 0x00007e00), 之后控制权就交给引导程序了.

不出意外的话, `pintos` 可能是以这样的命令来调用模拟器的

```bash
qemu-system-i386 \
-device isa-debug-exit \
-drive format=raw,media=disk,index=0,file=/tmp/tRmMf50TTo.dsk \
-m 4 -net none -nographic -monitor null
```

可以看到, `/tmp/tRmMf50TTo.dsk` 就是那个临时的虚拟磁盘.

### 到引导程序的执行

让我们追溯一下 `loader.bin` 是从哪里来的, 查看 `Makefile.build` 可以发现其来自于 `threads/loader.o`,
再往上就是 `threads/loader.S` 了.

```assembly

#### Kernel loader.

#### This code should be stored in the first sector of a hard disk.
#### When the BIOS runs, it loads this code at physical address
#### 0x7c00-0x7e00 (512 bytes) and jumps to the beginning of it,
#### in real mode.  The loader loads the kernel into memory and jumps
#### to its entry point, which is the start function in start.S.
####
#### The BIOS passes in the drive that the loader was read from as
#### DL, with floppy drives numbered 0x00, 0x01, ... and hard drives
#### numbered 0x80, 0x81, ...  We want to support booting a kernel on
#### a different drive from the loader, so we don't take advantage of
#### this.
```

有了上面的铺垫, 我们应该可以理解第一段注释的内容了吧. 基本可以看注释来试着理解它想做什么,
如果想要进一步可以自己了解一下 GNU Assembly 语法, 如果想要再深入一点, 可能就需要翻阅注释里
用 `[]` 框起来的参考文献了.

简单来说, 这段汇编的功能是初始化 segment registers 与 stack, 配置串口来输出, 成功的话会输出 `PiLo`
接着试图从磁盘中找到 pintos kernel, 输出这块磁盘, 比如 `hda1`. 将可执行文件加载到 0x00020000 的位置,
输出 `Loading............`, 这里的 `.` 可不是乱点的, 最多可以加载 512KB 的内核文件, 每 8KB 用一个
`.` 来表示. 我没有添加代码的时候生成的 `kernel.bin` 有 97.1KB, 对应这里输出了 12 个 `.`.

加载完成之后, loader 会找到入口地址, 把控制权转移给 kernel. 后面的内容才属于操作系统内核.

### Pintos, 启动

#### Low Level

前面 `threads/loader.S` 完成使命前最后执行的代码是 `ljmp *start`, 非常可惜, 这个 `start`
并不是我们想看到的 `main`, 它的定义在文件 `threads/start.S` 里面, 依旧是一段汇编.

```assembly
#### Kernel startup code.

#### The loader (in loader.S) loads the kernel at physical address
#### 0x20000 (128 kB) and jumps to "start", defined here.  This code
#### switches from real mode to 32-bit protected mode and calls
#### main().
```

开头的注释表明了这个文件的功能主要是让 CPU 从 16-bit 的 "real mode" 切换到 32-bit 的
"protected mode". 切换之后总算看到我们想要的 `call main` 了.

#### High Level

现在把注意力转移到 `threads/init.c` 的 `main()` 函数中, 现在我们的 CPU 处于 32-bit 的保护模式,
并且启用了分页机制, 内存布局如下

```text
+------------------+  <- 0xFFFFFFFF (4GB)
|      32-bit      |
|  memory mapped   |
|     devices      |
|                  |
/\/\/\/\/\/\/\/\/\/\
/\/\/\/\/\/\/\/\/\/\
|                  |
|      Unused      |
|                  |
+------------------+  <- depends on amount of RAM
|                  |
|                  |
| Extended Memory  |
|                  |
|                  |
+------------------+  <- 0x00100000 (1MB)
|     BIOS ROM     |
+------------------+  <- 0x000F0000 (960KB)
|  16-bit devices, |
|  expansion ROMs  |
+------------------+  <- 0x000C0000 (768KB)
|   VGA Display    |
+------------------+  <- 0x000A0000 (640KB)
|  pintos kernel   |
+------------------+  <- 0x00020000 (128KB)
|  page tables     |
|  for startup     |
+------------------+  <- 0x00010000 (64KB)
|  page directory  |
|  for startup     |
+------------------+  <- 0x0000f000 (60KB)
|  initial kernel  |
|   thread struct  |
+------------------+  <- 0x0000e000 (56KB)
|        /         |
+------------------+  <- 0x00007e00 (31.5KB)
|   pintos loader  |
+------------------+  <- 0x00007c00 (31KB)
|        /         |
+------------------+  <- 0x00000600 (1536B)
|     BIOS data    |
+------------------+  <- 0x00000400 (1024B)
|     CPU-owned    |
+------------------+  <- 0x00000000
```

接着还是初始化, 我们调用各种关键模块, 执行对应的 `<module>_init()` 函数.
有些模块的初始化有先后顺序, 比如 `thread_init()` 之后我们才可以使用 `lock` 之类的 synchronization
primitives; 又或者 `console_init()` 之后我们才可以用 `printf()` 输出信息.

当初始化全部结束之后, 我们可以看到 `Boot complete.`, 接着就是 `run_actions()`,
里面跑的就是我们传入的参数. 在 proj1 中我们会调用特定函数来完成测试, 剩下的三个 proj 都是通过执行
userprog 的方式来完成测试.
