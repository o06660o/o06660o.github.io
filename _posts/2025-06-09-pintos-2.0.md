### 一个可能遇上的 BUG

`pintos -- -q` 居然无法正常显示 `Boot Complete`, 然而我们做 Proj1 之前至少是可以启动的.
甚至 bochs 模拟正常而 qemu 模拟不正常.

我在经过检查之后发现我没有正确的处理 `sema_up()` 中 "This function may be called from an interrupt
handler" 这个信息, 在不合适的时机调用了 `thread_yield()`, 我的解决方案是加了一个判断
`!intr_context()`.

```c
/* Up or "V" operation on a semaphore.  Increments SEMA's value
   and wakes up one thread of those waiting for SEMA, if any.

   This function may be called from an interrupt handler. */
void
sema_up (struct semaphore *sema)
{
  enum intr_level old_level;

  ASSERT (sema != NULL);

  old_level = intr_disable ();
  struct thread *max_waiter = NULL;
  if (!list_empty (&sema->waiters))
    {
      max_waiter = thread_list_max (&sema->waiters);
      list_remove (&max_waiter->elem);
      thread_unblock (max_waiter);
    }
  sema->value++;
  if (!intr_context () && max_waiter != NULL
      && thread_less (thread_current (), max_waiter))
    thread_yield ();
  intr_set_level (old_level);
}
```

当然你的情况可能和我不一样, 你也可以试试看
[这里](https://github.com/CCXXXI/pintos/wiki/Project%E2%85%A1)
给出的方案.

### 所谓用户程序

从这个 proj 开始, 测试将会通过运行 userprog 的方式来完成.

那么什么是 user program 呢, 这就与我们平常接触的 C 程序比较类似了, `examples/` 文件夹里面就是例子.

```c
#include <stdio.h>
#include <syscall.h>

int
main (int argc, char **argv)
{
  int i;

  for (i = 0; i < argc; i++)
    printf ("%s ", argv[i]);
  printf ("\n");

  return EXIT_SUCCESS;
}
```

这就是一个简单的 `echo.c`, 它似乎与我们写的 C 程序还有一点不太一样. 更具体地说, 它用的不是
`return 0` 而是 `return EXIT_SUCCESS`. 事实上, 这里面的 `stdio.h` 也不是我们熟悉的那个,
而是 `lib/stdio.h`, 看来我们的 C 程序只可以使用 pintos 给我们的功能.

接着我们再看看 `make` 生成的可执行文件

```text
$ file echo
echo: ELF 32-bit LSB executable, Intel i386, version 1 (SYSV), statically linked, with debug_info, not stripped
```

这是一个静态链接的 ELF 文件, 它可以被 pintos 所执行. 而执行的过程可以看 `userprog/process.c` 里面的
`load()` 函数, 我们可以看看它的注释:

```c
/* Loads an ELF executable from FILE_NAME into the current thread.
   Stores the executable's entry point into *EIP
   and its initial stack pointer into *ESP.
   Returns true if successful, false otherwise. */
bool
load (const char *file_name, void (**eip) (void), void **esp)
{
  /* ... */
}
```

加载完成之后我们有了正确的 `eip` 与 `esp` 寄存器, 随后会切换到用户态, CPU 将会从
`eip` 指向的地址开始执行指令. 而获取命令行参数, 环境向量之类的额外信息需要通过 `esp` 来读取.
~~然而这里 `esp` 指向的栈空间里面没有命令行参数, 这是我们需要完成的内容~~

### 从简单的 echo 开始

我们的目标是让我们的第一个用户程序: `echo` 可以正常工作, 也就是 `pintos -- -q run "echo foo bar"`
可以有正确的输出.

然而我们无法启动系统, 关键报错是 `No file system device found, can't initialize file system.`
这里直接给出解决方案 (假设目前位于 `userprog/build/`), 想要深入研究的可以看
[这里](https://pkuflyingpig.gitbook.io/pintos/project-description/lab2-user-programs/background#create-your-simulated-disk-file-system)

```bash
pintos-mkdisk filesys.dsk --filesys-size=2
pintos -- -f -q
cd ../../examples/
make
cd ../userprog/build/
pintos -p ../../examples/echo -a echo -- -q
```

简单来说我们就是创建了一个虚拟磁盘, 然后把 `echo` 放入了文件系统. 执行 `pintos -- -q ls` 就可以看到

```text
Files in the root directory:
echo
```

然而执行 `pintos -- -q run "echo foo bar"` 看到的输出是

```text
Executing 'echo foo bar':
Execution of 'echo foo bar' complete.
```

这是因为 `process_wait()` 直接 `return -1` 而没有给用户程序执行的机会. 那么我们先简单粗暴加入一个
`timer_sleep(TIMER_FREQ);`, 得到的信息是 `load: echo foo bar: open failed`.
这个问题是因为我们没有完成 argument passing, 我们试图去加载一个叫做 `echo foo bar` 的文件,
它并不存在. 接下来我们需要完成 argument passing. 现在输出变成了这样.

```text
Executing 'echo foo bar':
system call!
Execution of 'echo foo bar' complete.
```

并没有我们想要的输出, 但是这里的信息提示我们需要实现几个 system calls. 我们需要试着完成 `write()`
这个 system call. 我们其实不需要完整的完成它, 只需要考虑输出到终端, 也就是 `fd == STDOUT_FILENO`
的情况. 到了这一步, 你应该清楚如何完成剩下的部分了.

## Task 2: Argument Passing

### 明确需求

我们的程序都有一个 `int main(int argc, char **argv)`, 我们的任务就是让它找到正确的 `argc`, `argv`.
虽然这看上去无从入手, 但我们只需要往 user stack 里面填充正确二进制格式的数据就可以了. 填充 user
stack 的方式就是操纵 `esp` 寄存器. 具体格式可以看
[这里](https://pkuflyingpig.gitbook.io/pintos/project-description/lab2-user-programs/background#argument-passing)

### 分析

我们现在应该知道 pintos 中执行用户程序的方式了, 依旧拿 `pintos -- -q run "echo foo bar"` 为例子,
我们其实调用了 `process_execute("echo foo bar")`, 我们需要在一个合适的位置来分割这些参数,
`load()` 可以吗? 个人认为这个函数本身就比较长, 不太建议往里面塞东西了. 所以我选择修改
`process_execute()`.

分割输入字符串部分我们可以使用 `lib/string.c` 提供的 `strtok_r()` 函数. 我们首先需要传递正确的
userprog 名称, 先找到需要传递名称的函数, `process_execute()`, `start_process()`.
但是要注意这个函数会修改传入的第一个字符串, 所以在 `process_execute()`
中应该需要建立一个副本来提取名称, 否则 `start_process()` 中获得的字符串可能不正确.

接着我们就要往 user stack 填充数据了, 我拉出来了一个 `uint8_t esp = is_.esp` 来修改,
原因是后面 debug 调用 `hex_dump()` 的时候可以有一个正确的大小. 关于数据对齐, 可以用优雅的位运算
`esp = (uint8_t *)((uintptr_t)esp & ~3);`, 中间跳过的数据不清零应该没事吧.

### 检查

只完成这个 Task, 应该还是跑不通任何测试点, 不过我们可以通过 `hex_dump()` 来检查.
假设传入 `echo foo bar`, 在传参结束后加上

```c
size_t buf_size = (uint8_t *)if_.esp - esp;
hex_dump ((uintptr_t)esp, esp, buf_size, true);
```

如果没错误估计会看到下面的输出.

```text
bfffffd0              00 00 00 00-03 00 00 00 e0 ff ff bf |    ............|
bfffffe0  f3 ff ff bf f8 ff ff bf-fc ff ff bf 00 00 00 00 |................|
bffffff0  00 00 00 65 63 68 6f 00-66 6f 6f 00 62 61 72 00 |...echo.foo.bar.|
```

那么这个怎么看呢, 以最后一行内容为例. 中间用 `-` 隔开的两段是以十六进制表示的 8 * 2 字节内存.
前面的 `bffffff0` 是内存地址, 指向中间内存段的第一个 (最左边的) 字节, 而右边就是中间内存对应的 ASCII 值.

- `bffffff0` -> `00` -> `.`
- `bffffff1` -> `00` -> `.`
- `bffffff2` -> `00` -> `.`
- `bffffff3` -> `65` -> `e`

## Task 3: Accessing User Memory

> User virtual memory is per-process.
> Kernel virtual memory is global.
> A user program can only access its own user virtual memory.
> Kernel threads can access both kernel virtual memory and, if a user process is running,
> the user virtual memory of the running process.

这一部分官方文档介绍的比较详细了, 并且给出了两种思路. 我选择第二种方案.

第二种方案大概只需要做两件事: 第一个是确保用户传入的指针指向 user address space,
第二个是在 `page_fault()` 被触发的时候识别出其原因是解引用非法指针.

最后根据你 system call 的实现, 可能需要把 `kill()` 里面 `SEL_UCSEG` 的处理中 `thread_exit()`
函数修改成正确的终止进程函数.

## Task 4: System Calls

### Subtask 4.1: System Call Handler

#### 明确需求

大部分操作系统都有很多系统调用 (虽然只有一个系统调用也不是不行), 为了让程序更具可扩展性,
我们需要有一个 handler. 在 pintos 中就是位于 `userprog/syscall.c` 的 `syscall_handler()`.

#### 分析

回想一下 x86-32 架构下的系统调用是如何实现的, 是 `int $0x30` 中断. 所以我们需要根据
`struct intr_frame *f` 来知道现在应该做什么, 进一步说, 我们需要知道现在正在执行哪一个系统调用,
这个系统调用又传入了哪些附加信息, 处理完成之后还需要把返回值放置在 `eax` 寄存器里面.

至于怎么获取信息呢, 我们可以寻找一下代码中造成 `int $0x30` 中断的部分, 这在 `lib/user/syscall.c` 中.
里面的函数让我们的用户程序有办法发起系统调用, 而整个文件最关键的部分其实是最前面的几个宏

```c
/* Invokes syscall NUMBER, passing arguments ARG0, ARG1, and
   ARG2, and returns the return value as an `int'. */
#define syscall3(NUMBER, ARG0, ARG1, ARG2)                                    \
  ({                                                                          \
    int retval;                                                               \
    asm volatile ("pushl %[arg2]; pushl %[arg1]; pushl %[arg0]; "             \
                  "pushl %[number]; int $0x30; addl $16, %%esp"               \
                  : "=a"(retval)                                              \
                  : [number] "i"(NUMBER), [arg0] "r"(ARG0), [arg1] "r"(ARG1), \
                    [arg2] "r"(ARG2)                                          \
                  : "memory");                                                \
    retval;                                                                   \
  })
```

我们的用户往栈空间里面压入了数据, 唤起中断来让内核处理. 我们对用户的输入不可以做出任何假设,
用户输入分为两种, 一种是传值, 一种是传指针. 这里建议阅读 task3: accessing user memory 的内容.

### Subtask 4.2: Implement 13 System Calls

一般来说, 系统调用的具体实现应该分散到不同模块里面, 整个 `userprog/syscall.c` 里面只需要调用接口即可.

#### Halt

这个最简单, 只需要调用 `devices/shutdown.h` 里面的 `shutdown_power_off()` 即可.

#### Exit && Wait && Exec

> Implementing this system call requires considerably more work than any of the rest.

在 pintos 原来实现的代码中, `thread_exit()` 会调用 `process_exit()`, 我不是特别理解,
所以我把两个函数的调用关系修改了, 也就是 `process_exit()` 调用 `thread_exit()`.

做出上面的修改之后, 我们实现系统调用可以选择 `process_exit()`, `process_wait()`, `process_exec()`
这三个函数. 那么我们的任务就是进一步补全它们.

首先是 `process_exec()`, 我们还需要做的是让子进程创建完成之后再返回, 可以使用 `struct semaphore`
来实现. 注意这个信号量需要让父进程来控制, 否则我们 `sema_down()` 可能会试着等待一个非法的信号量.

接着是 `process_wait()`, 关键是获取死去的子进程的退出信息, 这个东西不能存储在子进程里面,
我的想法是使用 `malloc()` 动态分配, 并用一个哈希表来查找. 退出信息只会在这里用上,
如果父进程先于子进程被终止, 这些信息就不重要了. 但是 `free()` 可以放在 `process_exit()` 里面吗?
由于 `initial_thread` 的退出是通过 `thread_exit()`, 那么释放资源可能还是得放在 `thread_exit()` 里.

#### Others

剩下的系统调用的共同点是, 它们都与文件系统有关.

> You should use synchronization to ensure that only one process at a time is executing file
> system code.

虽然这边要实现的 syscall 似乎比较多, 但其实关键函数已经写好了, 我们可以调用
`filesys_create()`, `filesys_remove()`, `filesys_open()`, `file_length()`,
`file_read()`, `file_seek()`, `file_tell()`, `file_close()`.

需要注意目前 file system 的实现不支持并发, 我选择往 `filesys/filesys.h` 放一把大锁保平安,
强制使同一时间只有一个线程有能力使用文件系统. (关于并发控制的更多内容, 看下面补充部分)

当然事情没有那么简单. 我们发现这些 syscall, 有些传入 `const char* file`, 有些则是传入 `int fd`.
但是我在 `filesys/` 下似乎没有找到所谓 `fd` 的定义, 也许我们可以自己实现 `fd` 的分配 (参考 `tid_t`)
至于两者之间的转换, 可以使用哈希表. (我自己用哈希表实现过, 保证可行. 对不上源码的原因是我队友用了
`bitmap`)

剩下应该还是好操作的吧. 顺便提醒一下, `fd` 只对创建它的线程而言是合法的, 如果其他线程询问这个 `fd`,
它并不能访问这个"file descriptor".

### 一些问题

- 请不要忘记使用文件系统的时候加锁, 比如 `process_execute()` 就需要, 另外做了下面 Task5 之后
  `process_exit()` 可能也需要.
- 对于 passing invalid argument 的处理我感觉比较耐人寻味, 什么时候应该杀死进程,
  什么时候只需要返回非法结果, 至少我不保证我的写法一定正确.

## Task 5: Denying Writes to Executables

我们可以使用函数 `file_deny_write()` 来实现需求, 不过这里不需要调用 `file_allow_write()`,
在线程生命结束时直接 `file_close()` 即可. 需要注意 `load()` 函数 `goto done` 之后无论是否成功都有一个
`file_close()`, 记得把它改了.

## 补充

- 关于 `pid_t`, 它的定义在文件 `lib/user/syscall.h` 里. 目前它与 `tid_t` 是一一对应的.
- 目前的文件系统对文件名长度有一个上限 `NAME_MAX`, 它的定义在 `filesys/directory.h`.
- 如果你想要调试用户程序的函数, 有一个很重要的 macro 叫做 `loadusersymbols`, 一个样例用法是
  `loadusersymbols tests/userprog/exec-multiple`.
- 在我开始做 proj4 的时候, 我突然意识到一个 `extern struct lock` 是非常愚蠢的, 我们在 proj2
  可以把这个锁局限在 `filesys/filesys.c` 内部. 但是我这样做完之后确实可以通过 proj2 的所有测试点,
  但是 proj3 中确实遇上了问题, 所以这里的并发控制值得再想一想.

### ex-test1

我们会下意识假设子进程先与父进程终止, 而且公开测试点似乎也没有相关的测试.
我受到 `recursor.c` 启发随便写了一个测试点, 至少它帮我测出了一处 use after free 的 bug.
~~毕竟是用脚写的, 所以实现等待直接 busy waiting, 可能需要根据你的机器性能做出调整~~

```bash
cd ../../examples/ && \
make && \
cd ../userprog/build/ && \
pintos --filesys-size=2 -p ../../examples/test1 -a test1 \
-- -q -f run "test1 qwq 3 0"
```

```c
/* test1.c

   Currently, this file tests the behavior when a parent process terminates
   before its child.

   I made some changes to recursor.c and creates 4 processes:
   3 -> 2 -> 1 -> 1
   hoping their termination order to be:
   0 -> 2 -> 1 -> 3
   however, under my implementation it is:
   2 -> 3 -> 0 -> 1
*/

#include <stdio.h>
#include <stdlib.h>
#include <syscall.h>

int
main (int argc, char *argv[])
{
  char buffer[128];
  pid_t pid;
  int retval = 0;

  if (argc != 4)
    {
      printf ("usage: test1 qwq 3 0\n");
      exit (1);
    }

  /* Print args. */
  printf ("%s %s %s %s\n", argv[0], argv[1], argv[2], argv[3]);

  /* Execute child and wait for it to finish if requested. */
  if (atoi (argv[2]) != 0)
    {
      snprintf (buffer, sizeof buffer, "test1 %s %d %s", argv[1],
                atoi (argv[2]) - 1, argv[3]);
      pid = exec (buffer);

      if (*argv[2] == '3')
        for (volatile int i = 0; i < 1000000000; i++)
          asm volatile ("");
      if (*argv[2] == '2')
        for (volatile int i = 0; i < 50; i++)
          asm volatile ("");
      if (*argv[2] == '1')
        for (volatile int i = 0; i < 500; i++)
          asm volatile ("");

      if (atoi (argv[3]))
        retval = wait (pid);
    }

  /* Done. */
  printf ("%s %s: dying, retval=%d\n", argv[1], argv[2], retval);
  exit (retval);
}
```
